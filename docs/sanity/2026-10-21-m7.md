## 4. Pattern inconsistency — WATCH (stable)

- Good: new modules follow house style (module docstring citing FR, Google docstrings with Raises,
  `Depends(engine)`, `apply.NotFoundError` for 404, ADR-0029 for the new registered writer,
  `write_transaction` for writes, `StepKind` in `kb/vocab.py` with a CHECK constraint via `_in`).
- **Low-Medium (4a, carried, not fixed)** failure handling on model-calling routes.
  `api/learning.py:make_plan` uses `HTTPException(502, failure_message(exc))` with no logging, which
  matches `discovery.py` but not `chat.py` (logs a warning) or `cvs.py:edit_cv` (hand-built message).
  Four routers now, three styles. One `run_agent_or_502` helper would close it.
- **Low (4g, new, behaviour)** `learning/progress.py:propose_completion` returns the earlier id
  whenever `completion_proposal_id` is set, even after that proposal was **rejected**. A rejected
  "confirm the skill" proposal therefore cannot be raised again from the plan, and the client is
  handed the stale (rejected) proposal. Code-read only; `tests/unit/test_learning_progress.py` has
  no test for completion after a rejection. Decide intended behaviour (re-raise when the earlier one
  is not pending) and test it.
- **Low (4h, new)** `api/learning.py:complete` calls `require_learning` and then, after
  `complete_step`, `propose_completion` calls it again (two reads of the entity per call); the first
  call is deliberate so a non-learning entity does not get steps marked, but the second is redundant
  when incomplete steps remain only because `propose_completion` returns early first. Harmless;
  mention so it does not get "tidied" into a bug.
- **Low (4i, new)** `progress.py:62` records the manual source and evidence text as the system's own
  sentence ("All N steps ... were marked complete"), while the module docstring says it records "the
  user's own statement". The evidence supports the proposal honestly (the user did tick the steps),
  but align the docstring or the text. Evidence is created before the proposal is reviewed; a
  rejected proposal leaves an orphan source/evidence row (same pattern as M6 4e, consistent).
- **Low (4j, new)** `api/learning.py:_recorded_entity` loops every `EntityKind` calling
  `find_by_name` and `get_entity` per match, in the request path; exact-name match only, so
  "Kubernetes" vs "k8s" never links and the plan then has `entity_id = None` (and completion is
  then a 409 forever). Documented by `require_learning`'s message; consider an alias lookup.
- **Carried:** M6 4b (`cv/validate.py` imports private `_set_status`), 4c (tuple error signal),
  4d (zero sentinel ids in `submit_interview`), 4f (`finalise` unused `response`), CLAUDE.md

## 5. Architectural drift — HEALTHY

**Boundaries.**
- `llm/` must not import `kb.apply`: grep of `src/cvforge/llm` for `kb.apply` / `import apply` finds
  only a docstring mention in `llm/settings_store.py:4`. `llm/agents/plan.py` imports only

- `api/` must not bypass `kb/`: `api/learning.py` imports `kb.apply` (error type only), `kb.queries`
  (read), `jobs.store`, `match.store`, `learning.*`, `llm.agents.plan`; no SQL, no table import.
- `kb/queries.py` must not write: unchanged, no insert/update/delete.
- `learning/` imports no `llm`; `learning/progress.py` imports `kb.apply`, `kb.intake`, `kb.queries`.
  No cycle.

**Registered-writer registry: 7 writers, as expected.** `tests/unit/test_write_path_invariant.py`
holds `llm/settings_store.py`, `kb/embeddings.py`, `jobs/store.py`, `match/store.py`, `cv/store.py`,
`cv/applications.py`, `learning/store.py` (allowance `learning_plan`, `learning_step` only), and
`test_registering_a_writer_is_a_visible_change` pins the exact set. The scan passes. Checked by
hand: `learning/store.py` writes only those two tables plus the `completion_proposal_id` column on
`learning_plan`; it does not touch `entity`, `edge`, `assertion`, `evidence`, `source` or `proposal`.
`CORE_KNOWLEDGE_TABLES` is a separate fixed set, so the allowance cannot silently widen. The M6
Low 5b ("registry starts empty" docstring) is **closed** (string no longer present). Only one
registry nit: the new `learning_plan.completion_proposal_id` is an FK from an advice table into
`proposal`; a registered writer holding a reference to a knowledge-adjacent table is fine, but note
that `proposal` deletion (if ever added) must handle it.

**Invariant 4 (completion only proposes `set_state`): holds.**
- `learning/progress.py:propose_completion` is the only completion path. It writes provenance through
  the public `apply.record_source` / `apply.record_evidence` entry points (which are in the reviewed
  `apply` surface; `test_apply_public_surface_is_exactly_the_reviewed_entry_points` passes) and then
  `intake.propose(...)` with exactly one `SetState(entity, CONFIRMED, evidence_id)` payload. It never
  calls `apply.commit`/accept; the entity stays `learning` until Álvaro accepts in review.
- `api/learning.py:complete` returns the pending proposal view; no route accepts it.
- The path cannot create an entity (`require_learning` demands an existing entity in `LEARNING`
  state) and cannot move it any other way. Idempotent: a second completion returns the same
  proposal (`test_completing_again_is_idempotent...`); the proposal goes through review/commit in
  `test_the_proposal_goes_through_review_and_commit_like_any_other`.
- Inv. 3: the `set_state` carries an evidence id bound to a `manual` source, so the proposed
  confirmation has provenance. Caveat (Low): the evidence is a system-worded statement that steps
  were ticked, i.e. self-attestation, not proof of the skill; the review gate is what makes this
  acceptable and the reviewer sees it as such.
- Inv. 1/5: the plan agent is tool-free and its output is stored in the advice tables only, never
  as assertions; nothing it says can reach a CV (plan tables are not read by `cv/`).
- Inv. 2: no new writer of entity/edge/assertion rows. Migration `0009` is in the exempt migrations
  directory and creates only the two tables.

**Untrusted data.** `plan_prompt` fences the posting requirement (`<requirement>`) and the skills
list (`<skills>`); `plan.md` says tag contents are data. The agent has no tools, so injected text
can neither read nor write. Requirement text is persisted indirectly only as the model's steps.
`tests/golden/test_prompt_injection.py` does not cover the plan agent (see 6). No new outbound calls.
