  family as the carried `JobView`/`StoredPosting` pair. *Remediation:* `from_attributes` on the

- **Low (1c, new)** `cv/store.py:95` and `cv/validate.py:59` both call `claim_problem(...)` with
  the identical eight-argument expansion of a claim. `claim_problem` (`cv/binding.py`) is the

## 5. Architectural drift — HEALTHY (no violations)

**Boundaries.**
- `llm/` must not import `kb.apply`: no import (only docstring mentions). `cv/` imports no `llm`
  and has no model call, Agent or prompt anywhere (`grep llm|Agent|prompt src/cvforge/cv` empty).
- `api/` must not bypass `kb/`: `api/cvs.py` imports `kb.apply` (errors), `kb.queries`, `cv.*`,
  `jobs.store`, `match.*`; `api/applications.py` imports only `cv.applications` and friends. No raw
  SQL beyond `sa.Engine` annotations. Both routers call `cv.*` rather than touching tables.
- `kb/queries.py` must not write: no insert/update/delete in it (new additions `get_assertion`,
  `entity_assertion_id`, `neighbours` extension are selects).
- Dependency direction `api -> cv -> {jobs, match, kb}` has no cycle. `cv/validate.py` imports
  `match.store` (reads matches), `cv/store.py` imports nothing from `match`. The M4 `llm <-> match`
  smell is unchanged (Low, carried): `llm/agents/adjacency.py:17` imports `match.verdicts` while
  `match/verdicts.py` imports `llm.settings_store`.

**Registered-writer registry: still sound at 6 writers (4 -> 6).**
- `tests/unit/test_write_path_invariant.py:52-59` now lists `llm/settings_store.py`,
  `kb/embeddings.py`, `jobs/store.py`, `match/store.py`, `cv/store.py` (`cv`, `cv_claim`) and
  `cv/applications.py` (`application`). The write-path test module passes (816 unit tests green): every other module is
  scanned for any write construct (AST, driver escapes, DML strings, `sqlite3`), and each
  registered writer is checked against *every table not in its own allowance*, so `cv/store.py`
  cannot touch `application` and `cv/applications.py` cannot touch `cv_claim`. The fixed
  `CORE_KNOWLEDGE_TABLES` test still prevents widening an entry to `entity`/`edge`/`assertion`.
  The set-equality test makes each new writer a visible, reviewed edit; both new ones came with
  ADR-0024 / ADR-0026.
- Verified by hand: `cv/store.py` references `schema.cv`, `schema.cv_claim`, and reads
  knowledge only through `kb.queries`; `cv/applications.py` references `schema.application` only.
  Neither writes `entity`, `edge`, `assertion`, `evidence` or any knowledge table. `cv_claim`
  rows are derived data like `match` (ADR-0024), so invariants 3 and 4 do not apply to them.
- Known limits, unchanged and not worsened: the scan checks *references*, not read-versus-write
  (a registered writer may SELECT a table outside its allowance only via `queries`, and the
  scan would flag a direct reference, which is the safe direction); aliasing a table through a
  variable is invisible. Six writers is the point where a registry that is a hand-edited dict
  starts to want a per-writer "tables read" column; not needed yet.
- **Low (5a)** the test module docstring is stale: "`REGISTERED_WRITERS` starts empty;
  `llm/settings_store.py` joins it in M1b task B1.3, `kb/embeddings.py` in B2." The registry
  holds six. Update the prose so the registry's own documentation doesn't mislead the next reader.

**Invariant 5 (automatic-mode CV never emits a claim without a stored assertion): structural,
with one soft spot.**
- Schema: `cv_claim.entity_id` and `assertion_id` are `NOT NULL` foreign keys
  (`schema.py`, migration 0005), `text` must be non-blank (check constraint), `slot` / `basis`
  are closed vocabularies. A line with no assertion cannot be inserted by any path.
- Generation: `cv/generate.py` is deterministic and has no model, prompt or tool; `_Builder`
  drops any fact lacking an assertion (`cv/facts.py:claim_source` returns None). A model
  therefore cannot emit text into a CV at all in automatic mode; the guarantee does not rest on
  prompt wording.
- Single door: the only insert into `cv_claim` is `save_cv`, which calls `claim_problem`
  (`cv/binding.py`) for every claim inside the write transaction, and nothing is stored if one
  fails. `claim_problem` requires the assertion to exist, target that entity, the entity to be
  `confirmed`, the text to equal the text recomputed from the live KB, and the assertion to be
  the one whose recorded value is that text. A claim placed under another entity's header must
  also cite an edge assertion relating them (migration 0007). The same function is reused by
  `validate_cv`, so store-time and present-time rules cannot diverge.
- Presentation gates: `render`, `download`, `validate`, `finalize_cv` and `create_application`
  all call `validate_cv` against the live KB; an application additionally requires `final`.
  Pinned by `tests/golden/test_cv_generation.py` (`unbacked_posting`, `sparse_kb` cases) and
  `tests/unit/test_cv_validate.py` (377 lines).
- **Medium (5b)** the `final` gate is convention, not structure: `cv.store.set_status` is public,
  takes any `CvStatus`, and its docstring says "Only `cv.validate.finalize_cv` may use this".
  Any caller can mark an unvalidated CV `final` and the DB check constraint allows it. Nothing
  in the code today does, and `create_application` re-validates anyway, so the damage is bounded;
  but "enforced by tests, not by wording" (CLAUDE.md invariant 5) applies here. *Remediation:*
  make it `_set_status` and expose only `finalize_cv` (and a `reopen` to draft if needed), or add
  a test asserting `set_status` is called only from `cv/validate.py` (AST call-site scan like the
  write-path test).
- **Low (5c)** a `period` claim cites one assertion (the start date) although its text states the
  end date too (`cv/facts.py:80-90`). `claim_source` does verify an end-date assertion exists, so
  the text is fully backed, but the claim records only one of the two ids; `read_claim` therefore
  shows evidence for the start only. *Remediation:* acceptable for M5; consider a second link
  column if the UI must show both spans.
- **Low (5d)** `GenerationMode.COLLABORATIVE` is storable but there is no collaborative editing
  route yet; when one lands, it must go through `save_cv`/`claim_problem` too (a free-text edit
  path would be the first way to author a claim not copied from a fact). Note for the FR that adds it.

**Untrusted data.** Claim text from the KB (which may derive from uploaded documents) reaches
LaTeX only through `latex_escape` (`cv/render.py`: backslash, braces, `& % $ # _ ~ ^`;
tested in `test_cv_render_output.py`); `latexmk` is called with a fixed argv, no shell, a
120 s timeout and the default (restricted) shell-escape setting. The output directory is derived
from the CV id, not user input. No outbound calls in `cv/`.
