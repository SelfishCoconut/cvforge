## 1. Duplication — **HEALTHY** (baseline)

- `src/`: pylint duplicate-code reports nothing. Grep found no same-shaped helpers.
  `cvforge.__version__` is read in two places (`app.py:27`, `api/health.py:30`).
  That is one canonical source consumed twice, not duplication.
- **Low** `.claude/hooks/guard_private_data.py:91-116` and
  `.claude/hooks/kb_write_path.py:54-85` share the same fail-open `main()` tail
  (emit JSON, `except Exception: pass`, `return 0`, `sys.exit(main())`). With only two
  hooks this is acceptable. *Remediation (when a third Python hook lands):* extract a
  `_hookio.py` with `emit(event, **fields)` and a fail-open `run(check)` wrapper, and
  keep it as the canonical copy.
- **Low** `.claude/hooks/format-on-edit.sh:6` and `.claude/hooks/remind-issue.sh:7`
  each carry their own inline `python3 -c 'json.load(sys.stdin)...'` payload parser.
  *Remediation:* fold them into the same shared helper as above, or leave them. The
  two lines are identical today, so the risk is only divergence.
- **Low / WATCH** `frontend/src/api.ts:1-4` (`interface Health`) is a hand-written
  copy of `src/cvforge/api/health.py:11-20` (`class Health`). One endpoint is fine,
  but at M1's API growth a hand-kept TS mirror of every Pydantic model is where drift
  starts. *Remediation (M1):* generate TS types from the OpenAPI schema that
  `tests/golden/snapshots/openapi.json` already pins (e.g. `openapi-typescript`), so
  the golden snapshot becomes the single contract.

## 4. Pattern inconsistency — **WATCH** (baseline)

`src/` is too small to drift: the modules share one style (Google docstrings,
full hints, a module docstring citing the ADR/NFR). The inconsistencies are in the
tooling around it.

- **Medium** Hook implementation style is split. `guard-private-data.sh` and
  `kb-write-path.sh` are thin `exec python3 <file>.py` wrappers. Their stated reason
  (`guard-private-data.sh:4-8`) is that inline Python in shell heredocs bricked the
  repo once and silently disabled the guard another time
  (`guard_private_data.py:11-20`). `remind-issue.sh:11-28` still uses that exact
  `python3 - <<'PY'` form, and `format-on-edit.sh:6` uses inline `python3 -c`.
  `remind-issue.sh` **does work today**: it reads the payload in a separate
  `python3 -c` first, and its heredoc program never reads stdin. My probe confirmed
  it emits context for `git switch -c` and stays silent for `ls`. It is still the
  pattern the project wrote down as fragile. *Remediation:* move
  `remind-issue.sh` logic to `remind_issue.py` behind a one-line wrapper, as its
  siblings do.
- **Low** `.claude/hooks/guard_private_data.py:58`: the docstring says "Raise Deny",
  but the exception is `DenyError` (`:49`). *Remediation:* fix the name.
- **Low** `frontend/src/App.tsx:7,19` carries an error `message` in `BackendState`,
  but `StatusBadge` ignores it and hard-codes the same string (`App.tsx:47`).
  *Remediation:* render `backend.message`, or drop the field.
- **Low** Doc/config drift: `CLAUDE.md:51` says "Python 3.12+", but
  `pyproject.toml:9` requires `>=3.13`, and `.python-version` and
  `docs/roadmap.md:24` say 3.13. *Remediation:* update `CLAUDE.md:51` to 3.13+
  (Álvaro's call, since it is the project-rules file).
- **Low** `.claude/hooks/guard_private_data.py:44` `FORCE_ADD` uses `.*` across the
  whole normalised command. Any Bash command that contains `git add` and a later
  `-f` flag for *another* program is denied, e.g. `git add README.md && rm -f build.log`
  (confirmed by probe). This audit tripped it twice: once on a probe payload, and
  once on the heredoc that wrote this report, because the heredoc text contained
  those tokens. The failure direction is safe, but a guard that cries wolf gets
  routed around (`guard_private_data.py:34-38` makes this same argument).
  *Remediation:* bound the match to one command segment, e.g.
  `\bgit\s+add\b[^;&|\n]*(-f\b|--force\b)`, and add the case to the hook test.

- **Must-fix / Medium** `.claude/hooks/kb_write_path.py:15` says
  *"see `tests/unit/test_hooks.py` for the cases this is held to"*. **That file does
  not exist**, and `git grep test_hooks` finds only that one reference. The same
  docstring (`:13-15`) warns that "a pattern that silently matches nothing is worse
  than no check at all, because it reads as a pass". The hooks guard the two
  highest-stakes properties in a public repo (private-data leakage and invariant 2).
  They are also outside every CI gate: ruff/format (`Makefile:7`,
  `ci.yml:25-26`), mypy (`pyproject.toml:76`), xenon (`ci.yml:29`) and coverage
  (`pyproject.toml:92`) all target `src tests scripts` only. They work today
  (verified by hand, above), but nothing stops them regressing. The documentation
  claims a gate that does not exist. *Remediation:* add `tests/unit/test_hooks.py`.
  It should drive `_check` / `_hits` directly with synthetic cases (deny data/,
  *.db, .env, CV-shaped names, the force-add flags, and a plain add of data/; allow
  `tests/data/`; fail open on garbage stdin; flag ORM, Core, sqlite3 and raw SQL; and
  skip `kb/apply.py`). Also add `.claude/hooks` to the ruff and mypy scope. At
  minimum, fix the docstring so it stops citing a test that does not exist.
